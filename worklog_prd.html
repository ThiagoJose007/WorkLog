Hierarquia de dados

Todo dado pertence a uma empresa. Abaixo dela, projetos agrupam demandas. Registros diários são entradas livres que referenciam demandas já criadas — eles não criam demandas, apenas as citam.

Empresa namespace raiz — dados 100% isolados
Projeto agrupador de demandas · N projetos por empresa
Demanda tarefa / reunião / alinhamento · vinculada a 1 projeto
Links externos Jira · Linear · Trello · GitHub · etc.
Registro de tempo timer ou lançamento manual
Registro diário entrada de data · referencia N demandas · tem imagens e notas
Relatório PDF visão semanal gerada a partir da hierarquia acima

Distinção crítica — Demanda vs Registro diário

Uma demanda é uma unidade de trabalho criada dentro de um projeto. Ela tem ciclo de vida, prioridade, timer e links.
Um registro diário é um log de "o que foi feito hoje". Ele referencia demandas existentes — não cria nem duplica. Um mesmo dia pode ter N demandas referenciadas.
O registro diário pertence à empresa ativa, mas pode referenciar demandas de qualquer projeto dessa empresa.

Regras de negócio

Isolamento de dados

RN-01 — Todo objeto (projeto, demanda, registro, membro) pertence a exatamente uma empresa. Nenhum dado é compartilhado entre empresas.
RN-02 — A troca de empresa deve ser explícita e confirmada. Nunca ocorre automaticamente.
RN-03 — Excluir empresa exclui todos os dados em cascata. Exige confirmação com digitação do nome.

Hierarquia Empresa → Projeto → Demanda

RN-04 — Uma demanda deve obrigatoriamente pertencer a um projeto. Não existe demanda "solta" na empresa.
RN-05 — Não é possível mover uma demanda para um projeto de outra empresa.
RN-06 — O tipo da demanda (tarefa / reunião / alinhamento) é imutável após criação. Para mudar: criar nova demanda.

Registro diário referencia demandas

RN-07 — O registro diário pertence à empresa ativa. Ele pode referenciar demandas de qualquer projeto dessa empresa.
RN-08 — O registro diário não cria demandas. Ele apenas vincula demandas existentes. A lista de seleção mostra somente demandas da empresa ativa.
RN-09 — Um registro deve ter ao menos: texto livre OU uma demanda referenciada OU uma imagem. Registro vazio não é salvo.
RN-10 — Uma demanda pode aparecer em múltiplos registros diários. Um registro pode referenciar múltiplas demandas.

Timer e tempo

RN-11 — Só pode haver um timer ativo por vez. Iniciar novo timer encerra o anterior automaticamente com aviso.
RN-12 — Demanda com status concluída ou cancelada não aceita novos lançamentos de tempo sem reabertura explícita.
RN-13 — Lançamento manual: data obrigatória, duração mínima de 1 minuto.

Links de ferramentas

RN-14 — Ao colar uma URL no campo de link, o sistema tenta detectar a ferramenta automaticamente pelo padrão de domínio. O usuário pode corrigir manualmente.
RN-15 — Uma demanda pode ter links ilimitados. Cada link tem: URL, label, ferramenta.

PDF

RN-16 — O PDF nunca mistura dados de empresas diferentes.
RN-17 — Imagens são redimensionadas para max 800px de largura. PDF limitado a 10 MB.
RN-18 — Links no PDF aparecem como texto clicável com URL completa.

Empresa → Projeto → Demanda → RegistroTempo / DemandaLink / DemandaImagem
Empresa → RegistroDiario → DiarioDemanda (referencia demandas, não cria)

## Persistência
- Dexie.js (IndexedDB) para todos os dados — nunca localStorage para objetos complexos

- Componentes em features/[dominio]/components/
- Cada feature tem seu próprio store Zustand
- Sempre TypeScript strict — sem any
- Demanda sempre tem projeto_id. RegistroDiario sempre tem empresa_id.

Prompts de correção frequente

Use estes prompts quando algo der errado:

O registro diário está sendo salvo com projeto_id mas ele não deve ter esse campo — pertence à empresa, não ao projeto. Corrija o schema Dexie, o store e todos os componentes que estejam passando projeto_id para o registro diário.

O timer está permitindo múltiplos timers ativos. Implemente a verificação global no store Zustand: antes de iniciar qualquer timer, buscar no Dexie por RegistroTempo com tipo = 'timer' e fim = null. Se existir, mostrar modal de confirmação para encerrar o anterior.

As demandas estão aparecendo no seletor de registro diário mesmo de outras empresas. Corrija o query para filtrar por empresa ativa: buscar projetos da empresa ativa → buscar demandas desses projetos → exibir agrupado por projeto.

Após import JSON, os dados aparecem duplicados. O import deve usar bulkPut (não bulkAdd) no modo mesclar — o bulkPut faz upsert por id, sobrescrevendo registros existentes em vez de duplicar.

Persistência, backup e portabilidade

O WorkLog roda como SPA estático — não há servidor nem banco de dados remoto. Toda a persistência é local no browser via IndexedDB. Esta seção explica a estratégia completa e os trade-offs.

Como os dados ficam armazenados

MecanismoO que guardaLimite prático
IndexedDB via Dexie.jsTodos os dados: empresas, projetos, demandas, registros, imagens em base64, registros de tempoCentenas de MB — anos de uso sem problema
localStorageSomente: empresa_ativa_id e preferências de UI (tema, sidebar)5 MB — não armazena objetos complexos aqui
Arquivo .jsonSnapshot completo exportado manualmente — backup, migração entre devices, versionamentoDepende do volume de imagens — em geral abaixo de 50 MB

Limitação principal e como contornar

Os dados ficam presos no browser daquele dispositivo. Abrir worklog.vercel.app em outro computador ou browser começa com banco vazio.

A solução é o ciclo de backup semanal: ao gerar o relatório PDF toda semana, exportar também o JSON. Guardar no Google Drive, Notion ou Dropbox. Ao trocar de máquina, importar o JSON mais recente.

SituaçãoSolução
Trocar de computadorExportar JSON no computador antigo → importar no novo
Limpar dados do browserRestaurar pelo último backup JSON
Usar em dois devicesExportar do principal → importar no secundário (modo somente leitura prático)
Corrupção de dadosRestaurar pelo último backup JSON

A migração da Fase 1 para a Fase 2 é quase sem código — Dexie Cloud é um wrapper sobre o Dexie.js existente. Da Fase 2 para 3, o schema Dexie vira um schema Postgres com poucas adaptações.

Deploy no Vercel

O WorkLog é um SPA estático — o Vercel serve o dist/ gerado pelo Vite como CDN global. Nenhum servidor, nenhuma variável de ambiente obrigatória na fase 1.

Passo a passo — primeira vez

#AçãoDetalhe
1Criar repositório no GitHubgit init && git remote add origin https://github.com/seu-user/worklog.git
2Commit inicialgit add . && git commit -m "init" && git push -u origin main
3Importar no Vercelvercel.com/new → Import Git Repository → selecionar worklog
4Configurar buildFramework: Vite · Build command: npm run build · Output dir: dist
5DeployVercel faz o build e entrega a URL worklog-xxx.vercel.app
6Domínio customizado (opcional)Settings → Domains → adicionar seu domínio

Arquivo vercel.json obrigatório para SPA

Sem este arquivo, rotas como /empresa/123/projeto/456 retornam 404 ao dar refresh, porque o Vercel tenta encontrar um arquivo físico naquele caminho.

{
  "rewrites": [
    { "source": "/(.*)", "destination": "/index.html" }
  ]
}

Coloque este arquivo na raiz do projeto, no mesmo nível de package.json.

CI/CD automático após setup

Depois do primeiro deploy, cada git push na branch main dispara um novo build automaticamente. O fluxo de trabalho fica:

# Desenvolver localmente
npm run dev

# Quando pronto, subir
git add .
git commit -m "feat: módulo de backup JSON"
git push

# Vercel detecta o push, faz build em ~30s e publica

Pull requests geram preview URLs automáticos — útil para testar antes de publicar na main.

O que acontece com os dados ao fazer novo deploy

Nada. Os dados estão no IndexedDB do browser do usuário, não no servidor. Deploy novo serve arquivos JS/CSS novos, mas o banco local não é tocado.

O único cuidado é com quebras de schema do Dexie: se uma nova versão do código muda a estrutura das tabelas, o Dexie precisa de uma migration (db.version(2).stores(...)). O Claude Code cuida disso se você mencionar "atualizei o schema" no prompt.
